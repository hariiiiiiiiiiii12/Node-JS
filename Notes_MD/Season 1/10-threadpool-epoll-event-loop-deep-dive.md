# Node.js — Event Loop Phases, Thread Pool and Networking Internals

## Additional Event Loop Phases

The event loop has more phases than just the commonly discussed ones.

Apart from the commonly known phases (Timers, Poll, Check, Close), there are additional internal phases.

One such phase is:

```
Idle / Prepare Phase
```

This phase runs before the **Poll phase**.

---

# Event Loop Cycle

A single full cycle of the event loop is called a **Tick**.

During each tick, the event loop goes through all its phases and processes callbacks associated with those phases.

```
One complete cycle of the event loop = Tick
```

---

# I/O Loop vs Event Loop

The terms **I/O loop** and **event loop** are often used interchangeably in Node.js.

Both refer to the mechanism that processes asynchronous events and callbacks.

---

# Deferred I/O Callbacks

Callbacks generated by I/O operations in the Poll phase can sometimes be deferred to the next event loop iteration.

This may happen due to:

- errors
- retries
- starvation situations

In such cases, the callback will be processed in the next event loop cycle.

---

# Thread Pool in libuv

When asynchronous operations such as file reading occur, they are offloaded to libuv.

libuv handles these tasks using a **thread pool**.

Example:

```
File reading
Cryptographic operations
DNS lookup
```

When an asynchronous task is delegated to libuv:

1. libuv assigns the task to one of the threads in the thread pool
2. The thread performs the operation
3. After completion, the thread becomes free again

---

# Default Thread Pool Size

The default size of the thread pool in Node.js is:

```
UV_THREADPOOL_SIZE = 4
```

This means only four tasks can run simultaneously in the thread pool.

---

# Changing the Thread Pool Size

The thread pool size can be increased using an environment variable.

Example:

```javascript
process.env.UV_THREADPOOL_SIZE = 5;
```

This increases the number of worker threads available to libuv.

---

# Example with Crypto Operations

Consider multiple cryptographic operations running simultaneously.

Example:

```
crypto.pbkdf2()
crypto.pbkdf2()
crypto.pbkdf2()
crypto.pbkdf2()
```

Since the thread pool size is 4, all four tasks can run in parallel.

Each task is assigned a separate thread from the pool.

---

# Order of Execution Is Not Guaranteed

Because multiple threads execute tasks simultaneously, the order of completion may differ.

Example:

```
Task 1
Task 2
Task 3
Task 4
```

Even if Task 1 starts first, another task might finish earlier.

Therefore:

```
Execution order is not guaranteed when thread pool tasks run in parallel.
```

---

# What Happens When More Tasks Are Submitted

Suppose five cryptographic tasks are executed:

```
crypto.pbkdf2() × 5
```

Since the thread pool size is 4:

- Four tasks start immediately
- The fifth task waits until a thread becomes available

Once a thread finishes its work, it becomes available for the next queued task.

---

# Do Incoming API Requests Use Thread Pool

Incoming HTTP requests to a server **do not use the thread pool**.

Thread pool is used mainly for:

- file system operations
- cryptographic operations
- some DNS functions

Network operations are handled differently.

---

# Networking in Node.js

Networking in Node.js is handled using **sockets**.

When a user sends a request to a server, a **TCP connection** is established.

To create and manage this connection, a **socket** is required.

Each socket has a **socket descriptor**, also known as a **file descriptor (FD)**.

---

# Problem with Thread per Connection Model

If every connection required its own thread, a server handling thousands of users would require thousands of threads.

This approach is inefficient and not scalable.

```
Thread-per-connection model is not practical for high concurrency systems.
```

---

# epoll and kqueue

Instead of using one thread per connection, operating systems provide scalable event notification systems.

Examples:

```
epoll (Linux)
kqueue (macOS / BSD)
```

These mechanisms allow a single process to monitor many connections simultaneously.

---

# epoll Descriptor

An **epoll descriptor** represents a collection of socket descriptors.

This means:

```
One epoll descriptor can monitor multiple socket connections.
```

This allows efficient handling of large numbers of network connections.

---

# How Node.js Interacts with the Operating System

Node.js runs as a process.

To communicate with the operating system kernel, it relies on mechanisms such as:

```
epoll
kqueue
```

libuv interacts with these kernel mechanisms to detect network activity.

---

# Example API Request Flow

Consider a server receiving multiple requests.

1. Multiple clients establish TCP connections
2. Each connection is represented by a socket descriptor
3. epoll monitors these sockets
4. When activity occurs on a socket, epoll notifies libuv
5. libuv generates a callback
6. During the Poll phase, the event loop processes the callback
7. The callback is pushed to the call stack
8. V8 executes the JavaScript code

This is how Node.js processes incoming API requests efficiently.

---

# Key Takeaways

- The event loop contains more phases than commonly discussed
- Idle and Prepare phases run before the Poll phase
- One complete event loop cycle is called a tick
- libuv manages a thread pool for certain asynchronous operations
- Default thread pool size in Node.js is four
- Thread pool tasks may finish in any order
- Incoming HTTP requests do not use the thread pool
- Networking is handled through sockets
- epoll and kqueue allow scalable handling of multiple connections
- libuv communicates with operating system mechanisms to detect network events
